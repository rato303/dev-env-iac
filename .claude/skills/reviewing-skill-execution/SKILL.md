# スキル実行レビュースキル

このスキルは、dev-env-iacプロジェクトで各スキル実行後の改善点を分析し、トークン使用量の最適化とユーザー体験の向上を支援します。

## 実行ケース

### ケースA: ユーザーからの指摘がある場合
- ユーザーがスキル実行後にトークンの無駄遣いを指摘
- 作業の進め方について改善提案がある
- 期待と異なる動作があった

**発動例**:
- 「さっきのcreating-issueスキル、同じファイルを3回読んでたよね？トークンの無駄じゃない？」
- 「planning-from-issueの実行、もっと効率的にできない？」

### ケースB: 能動的な改善点確認
- 指摘はないが、改善可能性を探る
- スキル実行のパフォーマンスを振り返る
- ベストプラクティスとの乖離を確認

**発動例**:
- 「今のplanning-from-issueの実行、改善点ないか確認して」
- 「committing スキルをレビューして」

## ワークフロー

### Phase 1: 実行コンテキストの収集

1. **対象スキル名を取得**
   - ユーザーが引数として指定（例: `/reviewing-skill-execution creating-issue`）
   - 引数がない場合はエラー

2. **対象スキルのSKILL.mdを読み込み**
   - `.claude/skills/{skill-name}/SKILL.md` を検索
   - ファイルが存在しない場合はエラー

3. **ワークフロー構造を解析**
   - Phase 1-4のセクションを抽出
   - 各Phaseの処理内容を把握
   - ツール呼び出しパターンを識別

**出力**:
- 対象スキル名
- SKILL.mdの内容
- ワークフロー構造の概要

### Phase 2: 改善点の分析

3つの観点から分析を実施します：

#### 2.1 効率性の観点

**チェック項目**:
- [ ] **重複ファイル読み込み**: 同じファイルパスへの複数のRead tool call
- [ ] **直列実行の非効率**: 独立したBash tool callが直列実行されている
- [ ] **不要なツール呼び出し**: 結果が使用されないツール呼び出し
- [ ] **部分読み込みの欠如**: 大きなファイル全体を読み込んでいる（offset/limit未使用）

**検出方法**:
- SKILL.mdのワークフロー記述から、ファイル読み込みパターンを抽出
- 「Phase 1でファイルAを読み込み」「Phase 2でファイルAを読み込み」→ 重複検出
- 「以下のコマンドを実行」が複数あり、「並列実行」の記載がない → 直列実行の可能性

#### 2.2 品質の観点

**チェック項目**:
- [ ] **プロジェクト規約準拠**: CLAUDE.mdの規約に従っているか
- [ ] **エラーハンドリング**: 適切な事前チェックとエラーメッセージがあるか
- [ ] **フィードバック品質**: ユーザーへの報告が明確か

**検出方法**:
- CLAUDE.mdを読み込み、コミット規約・PR規約との照合
- エラーハンドリングセクションの有無を確認
- エラーメッセージに「何が問題か」「どう対処するか」が含まれているか

#### 2.3 ユーザー体験の観点

**チェック項目**:
- [ ] **不要な確認プロンプト**: 安全な操作に対する過度な確認
- [ ] **実行ステップの明確性**: 各Phaseの目的が明確か
- [ ] **結果報告の分かりやすさ**: 結果サマリーと次のステップが提示されているか

**検出方法**:
- 「ユーザーに確認」の記述頻度をチェック
- 各Phaseのタイトルと説明の明確性を評価
- Phase 4（出力フェーズ）の構造を確認

### Phase 3: 改善提案の生成

検出された問題点ごとに、以下を生成します：

1. **問題点の整理**
   - 具体的な改善ポイントを箇条書き
   - トークン削減可能量の見積もり
   - 優先度の設定（High/Medium/Low）

2. **Before/After比較**
   - 現在のアプローチ（Before）
   - 提案するアプローチ（After）
   - 実装方法の具体的な手順

3. **トレードオフの説明**
   - 改善の利点
   - 改善の欠点（あれば）
   - 許容範囲の判断

**優先度の基準**:
- **High**: トークン削減効果 >30%、またはユーザー体験への影響大
- **Medium**: トークン削減効果 10-30%、実装容易
- **Low**: トークン削減効果 <10%、将来的な改善余地

### Phase 4: スキル定義への反映提案

1. **SKILL.mdの更新差分を生成**
   - 修正すべきセクションを特定
   - diff形式で修正内容を提示
   - Edit toolで直接適用可能な形式

2. **CLAUDE.mdへの反映判定**
   - プロジェクト全体の規約に影響するか
   - 他のスキルにも適用可能なベストプラクティスか
   - 該当する場合、追記内容を提案

3. **レビュー報告の出力**
   - `templates/review-report.md` の形式に従って出力
   - 検出された問題点、改善提案、反映提案を含む

**出力フォーマット**:
- Markdown形式
- セクション: 分析結果、検出された問題点、改善提案、スキル定義への反映提案、効果の見積もり

## エラーハンドリング

### スキル名未指定

**検出方法**: 引数が空

**エラーメッセージ**:
```
対象スキル名を指定してください。

使用方法:
  /reviewing-skill-execution <skill-name>

例:
  /reviewing-skill-execution creating-issue
  /reviewing-skill-execution planning-from-issue

利用可能なスキル一覧:
  ls .claude/skills/
```

### 対象スキルのSKILL.mdが見つからない

**検出方法**: `.claude/skills/{skill-name}/SKILL.md` が存在しない

**エラーメッセージ**:
```
スキル "{skill-name}" のSKILL.mdが見つかりません。

確認してください:
- スキル名が正しいか
- .claude/skills/{skill-name}/SKILL.md が存在するか

利用可能なスキル一覧:
{ls .claude/skills/ の結果}
```

### 分析結果が空（改善点なし）

**検出方法**: すべてのチェック項目がパス

**出力メッセージ**:
```
## スキル実行レビュー: {skill-name}

### 分析結果
実行は効率的で、検出された問題点はありません。このスキルはベストプラクティスに準拠しています。

### 評価内容

#### 効率性
- ✓ ファイル読み込みの重複なし
- ✓ 並列実行が適切に活用されている
- ✓ 不要なツール呼び出しなし

#### 品質
- ✓ プロジェクト規約に準拠
- ✓ エラーハンドリングが適切
- ✓ エラーメッセージが明確

#### ユーザー体験
- ✓ 確認プロンプトが必要最小限
- ✓ 実行ステップが明確
- ✓ 結果報告が分かりやすい

### 次のステップ

改善点は検出されませんでした。このスキルの設計をベストプラクティスとして、他のスキル開発時に参考にしてください。
```

## 使用例

### 例1: ユーザーからの指摘対応（ケースA）

**ユーザー**: 「さっきのcreating-issueスキル、同じファイルを3回読んでたよね？トークンの無駄じゃない？」

**スキル実行**: `/reviewing-skill-execution creating-issue`

**処理**:
1. `.claude/skills/creating-issue/SKILL.md` を読み込み
2. ワークフロー分析: Phase 1-3で `config/projects.yaml` を読み込み → 重複検出
3. トークン削減効果見積もり: 約6000トークン（67%削減）
4. 改善提案生成: Phase 1でのみ読み込み、変数に格納し再利用
5. SKILL.mdの修正差分を生成

**出力**:
```markdown
## スキル実行レビュー: creating-issue

### 分析結果
実行は概ね機能的ですが、効率性に改善の余地があります。特に、ファイル読み込みの重複が顕著です。

### 検出された問題点

#### 同一ファイルの重複読み込み (High)
- **カテゴリ**: 効率性
- **詳細**: `config/projects.yaml` を3回読み込んでいます
- **トークン使用量**: 約9000トークン（削減可能: 6000トークン、67%削減）

### 改善提案

**Before**:
Phase 1-3でそれぞれファイルを読み込み

**After**:
Phase 1でのみ読み込み、以降は変数を参照

**実装方法**:
1. Phase 1の冒頭で変数に格納
2. Phase 2-3では変数を参照

### スキル定義への反映提案

**ファイル**: `.claude/skills/creating-issue/SKILL.md`

```diff
 ### Phase 1: issue内容の準備
 
+**ファイル読み込みの最適化**:
+- この段階で必要なすべてのファイルを読み込み、変数に格納
+- Phase 2以降では変数を参照
+
 #### ケース1: ユーザーから直接指示がある場合
```

### 効果の見積もり

この改善により、トークン使用量を約6000トークン（67%）削減できます。
```

### 例2: 能動的な確認（ケースB）

**ユーザー**: 「今のplanning-from-issueの実行、改善点ないか確認して」

**スキル実行**: `/reviewing-skill-execution planning-from-issue`

**処理**:
1. `.claude/skills/planning-from-issue/SKILL.md` を読み込み
2. ワークフロー分析: Phase 1で並列実行を使用 → 効率的
3. エラーハンドリング確認: 事前チェックあり → 適切
4. 品質確認: CLAUDE.md規約に準拠 → 問題なし
5. 軽微な改善点のみ検出（優先度Low）

**出力**:
```markdown
## スキル実行レビュー: planning-from-issue

### 分析結果
実行は概ね効率的です。軽微な改善余地がありますが、優先度は低いです。

### 検出された問題点

#### プランファイル名の長さ制限が緩い (Low)
- **カテゴリ**: 品質
- **詳細**: slug生成時の最大文字数が50文字ですが、一部の環境でファイル名が長すぎる可能性
- **影響**: 軽微（ほとんどの環境で問題なし）

### 改善提案

オプションの改善として、slug最大文字数を40文字に短縮することを検討できます。

### 優先度
Low - 現状でも十分機能しています。必要に応じて対応してください。
```

## プロジェクト固有の規約

### 分析対象スキル

このプロジェクトの全スキルが分析対象です：

| スキル名 | 分析観点 |
|---------|---------|
| `creating-issue` | ファイル読み込み、テンプレート適用、gh CLI使用 |
| `planning-from-issue` | 並列実行、ファイル生成、メタデータ管理 |
| `executing-plan` | プラン読み込み、フェーズ実行、メタデータ更新 |
| `committing` | Git操作、規約準拠、並列実行 |
| `creating-pr` | Git操作、gh CLI使用、規約準拠 |
| `responding-review` | レビューコメント処理、ファイル修正、gh CLI使用 |

### トークン削減効果の見積もり基準

`references/analysis-criteria.md` の基準に従います：

#### 重複ファイル読み込み
```
削減トークン = (重複回数 - 1) × ファイルサイズ（文字数） × 0.75
削減率 = 削減トークン / 総トークン使用量
```

#### 並列実行化
```
トークン削減効果 = 0（トークンは削減されない）
実行時間短縮効果 = 約50-70%
```

### ベストプラクティスとの照合

`references/best-practices.md` の16パターンと照合：

1. 並列実行パターン
2. ファイル読み込みの並列化
3. Read Onceパターン
4. 部分読み込み（offset/limit）
5. Fail Fastパターン
6. 明確なエラーメッセージ
7. 回復可能なエラーへの対応
8. 進捗の明示
9. 結果サマリーの提示
10. 不要な確認プロンプトの削減
11. CLAUDE.md規約参照
12. 一貫性のある命名規則
13. 簡潔なSKILL.md記述
14. リファレンスファイルの活用
15. キャッシュ可能なデータの再利用
16. 遅延読み込み

### 分析レポートの保存

- レビュー報告は一時的な出力として表示（ファイル保存しない）
- ユーザーが「保存して」と指示した場合のみ、以下に保存：
  - `/tmp/skill-review-{skill-name}-{timestamp}.md`

### 他スキルとの連携

- **planning-from-issue**: レビュー結果を改善タスクとしてプランファイルに記録可能（将来拡張）
- **committing**: 改善提案を適用後、規約準拠のコミットを作成
- **creating-issue**: 大規模な改善が必要な場合、issueとして登録可能（将来拡張）
